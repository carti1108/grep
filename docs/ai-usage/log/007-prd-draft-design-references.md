Claude Code(Claude Fable 5.2), it-service-planner 플러그인의 prd-writer 스킬, planning-critic 에이전트 1개, 조사용 general-purpose 에이전트 1개.

## 요청

기획서를 먼저 만들고, 그에 따른 디자인 레퍼런스도 찾아 달라고 했다.

## AI 산출물

- `docs/planning/PRD.md` 0.2: 개요, 문제, 원인 가설, 지표, 대상, 해결 방향과 차별점, 범위, 사용자 스토리 11개, 사용자 흐름, 엣지 케이스, 리스크와 미검증 가정, 실험 계획, PO 판단 항목 9개
- `docs/planning/design-references.md`: 터미널 느낌을 쓴 제품, 명령어 입력 패턴, 휴대폰 입력, 색·글꼴 재료, 비슷한 서비스, 조심할 점, 조사에서 나온 설계 방향 7개
- `docs/planning/STATE.md` 수정: 0절(현재 단계), 4절(용어 "묶음", "넘길 글", "본문", "터미널 화면"), 13절(공백 8·16)
- 제안: MVP 범위와 우선순위, 북극성 지표, 명령어 이름, 넘길 글의 기본 내용

## 사람의 판단

- 인터뷰보다 기획서와 디자인 레퍼런스를 먼저 만들기로 한 것은 PO의 결정이다
- 기획서의 범위·지표·명령어, 새 용어 네 개는 PO가 아직 확인하지 않았다

## 검증

planning-critic이 기획서 0.1을 STATE와 경쟁 조사에 대조해 비평했다. 높음 9건, 중간 16건, 낮음 20건이 나왔고 0.2에서 고쳤다. 0.2는 다시 비평하지 않았다. `bash Scripts/check-docs.sh` 실행, 통과.

## 검증하지 못한 것 (있을 때만)

1. 디자인 레퍼런스는 페이지를 글로 읽은 것이라 화면 모양, 색, 글꼴을 눈으로 확인하지 못했다. 재검증도 거치지 않았다.
2. 기획서의 문제·원인·손해는 모두 가설이다. 인터뷰와 지표 트리가 없어 지표에 기준값이 없다.
3. 개발 범위를 산정하지 않았다.

## AI의 오류와 정정 (있을 때만)

1. 0.1은 차별점이 겨냥하는 두 원인(흩어짐, 다시 넣기)을 MVP가 해결한다고 썼으나, MVP 기능은 두 원인을 일부만 다뤘다. 0.2에서 다루는 범위와 다루지 않는 범위를 표로 적었다.
2. 0.1은 STATE의 반증 조건을 옮기면서 조건 하나를 빠뜨리고 하나를 줄여 썼다. 0.2에서 그대로 옮겼다.
3. 0.1의 북극성 지표는 단위가 다른 두 값을 더했고, 넘길 글에 무엇이 들어가는지가 절마다 달랐다. 0.2에서 지표를 바꾸고 넘기는 내용을 한 곳에 정의했다.
4. 0.1은 "저장 수단이 하나 더 늘 뿐일 수 있다"는 가정을 빠뜨렸다. 0.2의 리스크에 넣었다.
